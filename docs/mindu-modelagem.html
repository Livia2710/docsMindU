Modelagem do Backend — MindU

Documento no mesmo formato do roteiro da Aula 01 (Requisitos → Casos de Uso → Domínio → DER → Classes → Arquitetura), adaptado ao MindU com as decisões já fechadas em grupo.

1. Visão geral da aplicação

O MindU é um convênio de saúde mental corporativo. Uma Empresa contrata um Plano e recebe uma cota de matrículas para distribuir aos colaboradores. Cada Cliente (colaborador) se cadastra informando a matrícula recebida da Empresa; após aprovação da Empresa, completa o cadastro com dados sensíveis (CNS, nascimento, nome da mãe, sexo). O Profissional (psicólogo, psiquiatra etc.) se cadastra com foto, carteirinha, especialidade, local(is) de atendimento (presencial/virtual/híbrido) e disponibilidade; passa por aprovação de um Admin (perfil interno, uso exclusivo dos desenvolvedores) antes de aparecer nas buscas. O Cliente pesquisa Profissionais e agenda consultas.

Área Tecnologia
Front-End React (colega)
Back-End Spring Boot (Java), Spring Security, Spring Data JPA, JJWT, Lombok
Banco de Dados PostgreSQL
Autenticação JWT stateless + bloqueio por tentativas de login
Empacotamento Docker / docker-compose

2. Proposta de Planos (para validar com o grupo)

Como não há cobrança real (a Empresa só "escolhe" um plano, sem pagamento no sistema), a lógica dos planos serve para limitar quantas matrículas a Empresa pode distribuir. Sugestão de três níveis, alinhados ao porte da empresa (classificação comum no Brasil: pequena = ~10-49, média = ~50-499, grande = 500+ colaboradores):

Plano Porte indicado Matrículas inclusas (sugestão)
Plano Start Empresas de pequeno porte até 30 matrículas
Plano Essencial Empresas de médio porte até 100 matrículas
Plano Corporativo Empresas de grande porte até 500 matrículas (ou "sob consulta", vocês decidem um teto maior)

Os números são só ponto de partida — ajustem livremente. O importante para o modelo é que Plano tenha um campo vagasTotais, e a Empresa não deve conseguir gerar mais matrículas do que esse número permite (RN09).

5. Regras de Negócio (RN)

ID Descrição
RN01 Não é permitido cadastrar dois Clientes com o mesmo e-mail ou a mesma matrícula
RN02 Não é permitido cadastrar duas Empresas com o mesmo CNPJ
RN03 Senha mínima de 8 caracteres, para qualquer perfil
RN04 Matrícula deve pertencer à Empresa informada e estar disponível (não usada)
RN05 Cliente só completa a etapa 2 (dados sensíveis) após aprovação da Empresa
RN06 Profissional só aparece em buscas depois de aprovado por um Admin
RN07 Bloqueio de login: após 5 tentativas incorretas seguidas, a conta é bloqueada por 15 minutos. Contador zera após login bem-sucedido
RN08 Token de acesso expira após 60 minutos
RN09 O total de matrículas geradas por uma Empresa não pode ultrapassar vagasTotais do seu plano
RN10 Cliente só agenda consulta com Profissional aprovado, em horário compatível com a disponibilidade cadastrada e sem conflito com outro agendamento
RN11 Admin é um perfil de uso interno (equipe de desenvolvimento), sem tela pública de auto-cadastro

8. Fluxo de Cadastro do Cliente (detalhado)

sequenceDiagram
    actor Cliente
    participant ClienteController
    participant ClienteService
    participant MatriculaRepository
    actor Empresa

    Cliente->>ClienteController: POST /v1/clientes (nome, email, empresaId, matricula)
    ClienteController->>ClienteService: cadastrar(dto)
    ClienteService->>MatriculaRepository: findByCodigoAndEmpresa(matricula, empresaId)
    alt matrícula inválida ou já usada
        ClienteService-->>ClienteController: erro
        ClienteController-->>Cliente: 400/409
    else matrícula válida
        ClienteService->>MatriculaRepository: marcarComoReservada(matricula, cliente)
        ClienteService-->>ClienteController: cliente (status AGUARDANDO_APROVACAO)
        ClienteController-->>Cliente: 201 Created
    end

    Note over Empresa: mais tarde, no dashboard
    Empresa->>ClienteController: PATCH /v1/clientes/{id}/aprovacao (aprovado=true)
    ClienteController-->>Cliente: status = APROVADO

    Cliente->>ClienteController: PATCH /v1/clientes/{id}/dados-sensiveis (cns, nascimento, nomeMae, genero)
    ClienteController-->>Cliente: 200 OK (cadastro completo)

13. O que ainda falta decidir

  1. Valores exatos do plano (seção 2) — quantidade de matrículas por plano, ainda a validar com o grupo.
  2. Como a Empresa gera/distribui as matrículas — lote gerado automaticamente ao contratar o plano, ou a Empresa cadastra manualmente cada código? (impacta o endpoint de Matricula)
  3. Conflito de horário no agendamento (RN10) — validar contra Disponibilidade e contra outros Agendamentos do mesmo Profissional no mesmo horário; regra simples de sobreposição a implementar no AgendamentoService.
  4. Estratégia concreta de criptografia do CNS — AttributeConverter (Java, mais simples) vs pgcrypto (no banco); ambas resolvem, a primeira é mais fácil de implementar seguindo o nível das aulas.

Nenhum desses bloqueia começar a codar — dá para seguir com os packages da seção 11 e resolver 2–4 durante a implementação de cada módulo.
